# DrinkDiary 기능 감사 및 제품 방향 재정립

## 문서 정보

- 작성일: 2026-08-08
- 계기: 대규모 UI/GUI/VI 개편에 착수하기 전, 현재 기능이 사용자가 제시한 5가지 가치 기준을 충족하는지 먼저 점검

## 1. 감사 결과

사용자가 제시한 5가지 가치 기준 대비 현재 상태다. **5개 모두 갭이 있으며, 2·4·5번은 기능이 아예 존재하지 않는다.**

| # | 가치 기준 | 판정 |
| --- | --- | --- |
| 1 | 쉽게 음주 기록 추가 (SNS처럼) | 심각 |
| 2 | 테이스팅 노트를 칩으로 쉽게 작성 | 미구현 |
| 3 | 필터 UI가 결과를 가리지 않음 | 심각 |
| 4 | 설정에서 기록할 주종 선택 | 미구현 |
| 5 | 건강과 취향의 밸런스 인사이트 | 심각 (스키마 변경 필요) |

### 1.1 기록 추가 — 심각

현실적인 기록 1건에 **약 12~13탭**이 든다. 가장 큰 병목은 별점이다. `DDRatingInput`(`ui/component/Components.kt:501-525`)은 탭 가능한 별이 아니라 `-`/`+` 스테퍼이고 0.5씩 움직이므로, 기본값 0.0에서 4.0을 주려면 **`+`만 8번** 눌러야 한다.

그 밖에 확인된 마찰:

- 주류 종류가 미리 선택되어 있지 않다(`DrinkRecordInput.kt:5`에서 `null`). 사용자는 매번 종류부터 고른다.
- 사진은 폼 최하단에 있다(`RecordEditorScreen.kt:128-130`). Instagram이 사진에서 시작하는 것과 정반대 순서다.
- 실제로 강제되는 필수값은 **주종·이름·별점 3개**뿐인데(`SaveDrinkRecordUseCase.kt:23-35`), 검증 오류는 저장을 눌러야 비로소 표시된다. 입력 중 피드백이 없다.
- 임시저장·빠른추가·템플릿이 전혀 없다. `RecordEditorViewModel`은 `SavedStateHandle`을 쓰지 않고 평범한 `MutableStateFlow`(`:41`)에 상태를 두므로 **프로세스 종료 시 작성 중이던 내용이 전부 사라진다.** 취소·시스템 뒤로가기 모두 확인 없이 `popBackStack()`이다(`DrinkDiaryApp.kt:118`).
- 사진 선택 취소 시 `onImageSelected(null)`이 호출되어 **이미 고른 사진이 지워진다**(`Components.kt:423-476`).

### 1.2 테이스팅 노트 칩 — 미구현

`DDMultilineTextField("테이스팅 노트", ...)`(`RecordEditorScreen.kt:203`) 단일 자유 입력 하나가 전부다. 해당 컴포넌트(`Components.kt:314-323`)는 `minLines = 3`인 평범한 `OutlinedTextField`로, 플레이스홀더·자동완성·추천어·글자수 표시가 모두 없다.

**앱 전체에 다중 선택 칩 UI가 존재하지 않는다.** `FilterChip`은 컬렉션 필터에만 쓰이고 그마저 단일 선택이며, `AssistChip`은 읽기 전용 배지 용도다.

관련해서, 현재 "세부 평가"(`DrinkRatingBreakdown.kt:26-45`)가 향·산도·바디감·밸런스 같은 4개 항목에 별점을 매기는 방식으로 존재한다. 이는 칩과 목적이 중복된다 — 둘 다 "어떤 맛이었나"를 기록한다.

### 1.3 필터 UI — 심각

`FilterPanel`(`ui/collection/CollectionScreen.kt:110-128`)이 `LazyColumn` **바깥**에 형제로 배치되어 있어(`:87-104`) 스크롤과 함께 사라지지 않고 **상시 고정**된다.

폰 세로 기준 점유 높이: "종류" 라벨 16dp + 4dp + 칩 행 32dp + 10dp + "상태" 라벨 16dp + 4dp + 칩 행 32dp ≈ **114dp**, 여기에 리스트와의 간격 12dp와 외곽 패딩 16dp를 더하면 **약 140dp**가 첫 카드가 보이기도 전에 소진된다. 상단 앱바(64dp), 하단 내비게이션, 배너 광고(`showBannerAd = true`)까지 감안하면 결과 영역이 크게 좁아진다. 사용자가 지적한 바로 그 문제다.

가로 모드에서는 칩이 `fillMaxWidth()` 드롭다운으로 바뀌어(`Components.kt:774-781, 830-837`) **약 130dp로 오히려 더 커진다** — 세로 공간이 가장 부족한 상황에서 더 나빠지는 구조다.

접기/펼치기 상태가 아예 없고(`expanded` 변수 없음), 바텀시트나 필터 아이콘 버튼도 없다.

추가로 확인된 것:

- **텍스트 검색이 없다.** `DrinkRecordFilter`에 검색어 필드가 없고 DAO 쿼리에 `LIKE` 절이 없다. 이름·장소·노트로 찾을 방법이 없다.
- **정렬 컨트롤이 없다.** `ORDER BY recordedAtMillis DESC`가 SQL에 하드코딩(`DrinkRecordDao.kt:16`)되어 별점순·가격순 정렬이 불가능하다.
- **필터 축이 2개뿐이다.** `DrinkRecordFilter`는 `drinkType`과 `collectionStatus` 두 필드가 전부다(파일 전체 6줄). 날짜·별점·가격은 `DrinkRecord`에 저장되어 있는데도 필터로 연결되지 않는다.
- **하단 탭 왕복 시 필터가 초기화된다.** 내비게이션 콜백이 `popUpTo`/`launchSingleTop` 없이 `navigate()`만 호출하므로(`DrinkDiaryApp.kt:53, 60, 73`) 컬렉션 → 대시보드 → 컬렉션 시 새 백스택 항목과 새 ViewModel이 생성된다.
- 840dp 이상 넓은 화면에서는 필터가 좌측 240dp 컬럼으로 빠져 세로 비용이 0이다(`:66-85`). **폰은 이 분기에 해당하지 않는다.**

### 1.4 주종 커스텀 설정 — 미구현

`SettingsScreen.kt`는 **파일 전체가 45줄**이고, 화면 본문은 `DDFormSection("테마")` 하나에 `DDThemeModeSelector` 하나가 전부다. 테마 모드 외의 설정 항목이 없다.

`DrinkType`은 3값 고정 enum이며, **개별 값이 하드코딩된 곳이 6군데 이상**이라 "특정 주종 숨기기"를 넣으려면 선행 리팩터링이 필요하다:

- `ObserveDashboardSummaryUseCase.kt:29-34` — 주종별 카운트/평균을 각각 하드코딩한 6줄
- `DashboardSummary.kt:6-11, 18-26` — `Map`이 아니라 `wineCount`/`whiskeyCount`/`beerCount` 등 6개 개별 필드
- `Components.kt:1303-1316, 1422-1424` — "와인"/"위스키"/"맥주" 문자열 리터럴과 3개 블록
- `DashboardScreen.kt:136-141` — 명시적 3개 인자 전달
- `DrinkRatingBreakdown.kt:26-45` — 주종별 `when` 분기

한편 설정 추가 자체의 비용은 낮다. `ThemePreferenceRepositoryImpl.kt`가 SharedPreferences(`drink_diary_preferences`) + `MutableStateFlow` 미러 패턴을 이미 확립해 두었고, 새 설정 하나당 인터페이스 → 구현 → 유스케이스 2개 → `AppContainer` 배선 → ViewModel의 5계층을 따르면 된다.

### 1.5 건강·취향 인사이트 — 심각 (스키마 변경 필요)

`DrinkRecord`(`domain/model/DrinkRecord.kt:3-15`)의 전체 필드는 다음 11개다:

`id`, `type`, `name`, `imageUri`, `price`, `place`, `tastingNote`, `rating`, `ratingBreakdown`, `collectionStatus`, `recordedAtMillis`

**도수(ABV)·용량·잔 수·칼로리 등 건강 지표의 원천이 되는 필드가 하나도 없다.** `abv|alcohol|volume|session|calorie|streak`에 대한 대소문자 무시 grep 결과가 **0건**임을 재확인했다. Room 엔티티(`DrinkRecordEntity.kt:17-35`)도 동일하다.

`ObserveDashboardSummaryUseCase.kt:26-39`가 계산하는 12개 값은 전부 `records.size`, `.count {}`, `.average()` 중 하나다. 추세 기울기, 연속 기록, 전 기간 대비 증감 같은 파생 지표가 없고, `periodRange`(`:44-61`)는 현재 기간 하나만 계산하므로 **전 기간 대비는 지금 구조로 계산 자체가 불가능**하다.

"세션"(한 자리에서 여러 잔) 개념도 없다. 데이터 단위는 `DrinkRecord` 1건 = 술 1종 시음이다.

## 2. 재정립된 제품 방향

기존 방향은 "마신 술을 컬렉션으로 관리하고 재구매/비선호를 구분한다"였다(`usecase.md` 1절). 이 방향 자체는 유효하지만, **기록 자체가 무거워서 컬렉션이 쌓이지 않으면 뒤의 모든 가치가 성립하지 않는다.** 감사 결과 가장 큰 병목이 기록 단계에 있으므로 방향을 다음과 같이 재정립한다.

> **기록은 SNS만큼 가볍게, 회고는 데이터로 깊게.**

세 축으로 구체화한다.

**축 1 — 30초 안에 끝나는 기록.** 사진 한 장과 몇 번의 탭으로 끝나야 한다. 정교한 평가를 원하는 사용자를 위한 깊이는 남기되, **접힌 상태를 기본값으로** 두어 기본 경로에서 보이지 않게 한다.

**축 2 — 태그로 말하는 취향.** 자유 서술은 쓰기도 어렵고 나중에 집계도 안 된다. 테이스팅을 **선택형 태그**로 바꾸면 입력이 빨라지는 동시에, 태그 빈도라는 **집계 가능한 취향 데이터**가 생긴다. 축 3의 취향 분석이 여기에 의존한다.

**축 3 — 건강과 취향의 균형.** 지금은 "뭘 마셨나"만 답한다. 여기에 "얼마나 마셨나"(순수 알코올 환산)와 "뭘 좋아하나"(태그 프로파일)를 더해, 사용자가 스스로 균형을 잡을 수 있는 판단 재료를 준다. **경고하거나 통제하지 않고, 사실을 보여준다.**

이 방향에서 벗어나지 않는 원칙:

- 로컬 우선. 계정·서버 동기화·외부 주류 DB 연동은 계속 범위 밖이다(`usecase.md` 2절 유지).
- 건강 지표는 **정보 제공이지 의학적 조언이 아니다.** 문구와 면책 표기에 이 선을 명확히 둔다.

## 3. 기준별 목표 상태와 갭 해소 방안

### 3.1 기록 UX — Instagram 피드 작성 벤치마킹

**목표: 최소 4탭 + 이름 입력으로 저장 완료** (현재 12~13탭).

| 변경 | 내용 |
| --- | --- |
| 별점 입력 교체 | `DDRatingInput`의 `-`/`+` 스테퍼를 **탭 가능한 별 UI**로 교체한다. 별 위 좌/우 절반 탭으로 0.5 단위를 지원하면 4.0이 **8탭 → 1탭**이 된다. 이 하나가 단일 개선으로 가장 크다. |
| 사진 우선 | 사진 선택을 폼 최상단으로 올린다. Instagram과 동일하게 "사진 → 설명" 순서. 단 **사진은 계속 선택 사항**으로 둔다(사진 없이 마신 기록도 많다). |
| 주종 프리셀렉트 | 마지막에 기록한 주종을 기본 선택한다. 대부분의 사용자는 특정 주종에 편중되므로 적중률이 높다. 3.4의 "기록할 주종 설정"과 결합하면 주종이 1개일 때 이 단계가 아예 사라진다. |
| 실시간 검증 | 필수 3개(주종·이름·별점) 미충족을 저장 시점이 아니라 입력 중에 표시한다. 저장 버튼 활성화 상태로 남은 항목을 알린다. |
| 접기 기본값 | 가격·장소·기록일시를 접힌 보조 영역으로 내린다. 대시보드 캘린더에서 이미 검증한 `AnimatedVisibility` 접기 패턴을 재사용한다. |
| 사진 취소 버그 | 피커 취소 시 기존 사진이 지워지는 동작을 고친다(취소는 아무 것도 바꾸지 않아야 한다). |
| 임시저장 | `SavedStateHandle` 도입으로 프로세스 종료 시 작성 내용을 보존한다. 미저장 상태로 뒤로가기 시 확인 다이얼로그를 띄운다. |

### 3.2 테이스팅 칩 — 세부 평가 별점을 대체

**결정: 세부 평가 4항목 별점을 제거하고 태그 칩으로 통합한다.** 두 기능이 같은 질문에 답하고 있어 중복이며, "산도 3.5점"보다 "#새콤함"이 SNS식 기록에 맞고 입력도 훨씬 빠르다.

- 데이터 모델에 `tastingTags: List<String>` 신설. Room에는 구분자 결합 문자열 또는 별도 테이블로 저장한다(구현 시 결정).
- 기존 `detailRating1..4` 컬럼은 마이그레이션에서 정리한다. **기존 사용자 데이터 처리 방침을 마이그레이션 작성 시 명시적으로 결정**해야 한다(단순 삭제 vs 태그로 변환 시도).
- 주종을 고르면 해당 주종의 칩 세트가 노출된다. 어휘는 `research/tasting-vocabulary.md`에 조사 완료 — 주종별 4개 카테고리 × 8~15개 칩, 각 칩에 입문/전문 난이도 표기, 주종 공통 베이스 칩과 우선 노출 16개 추천까지 포함되어 있다.
- 기본은 **우선 노출 칩만 보여주고 "더보기"로 확장**한다. 입문 난이도 칩을 앞에 배치한다.
- 다중 선택을 지원하고, 목록에 없는 표현을 위해 **자유 입력 칩 추가**를 허용한다. 자유 서술 노트 필드는 남기되 선택 사항으로 유지한다.
- **어휘 검수 필요**: 조사된 칩 중 `알코올 스파이시`, `부드러운 목넘김`(각 8자), `쌉싸름한 단맛`(7자) 등이 권장 길이(2~5자)를 넘는다. UI 반영 전 축약하거나 대체어를 정한다.

### 3.3 필터 — 결과 영역 회복

- 필터를 상시 노출에서 **접히는 형태 또는 바텀시트**로 전환한다. 기본은 접힘이고, 적용 중인 필터는 접힌 상태에서도 요약 칩으로 보여 무엇이 걸려 있는지 알 수 있게 한다(대시보드 캘린더의 "이번 달 기록 N일" 요약과 같은 접근).
- 필터를 `LazyColumn` **안으로** 이동해 스크롤과 함께 흐르게 한다. 대시보드에서 고정 높이 요소를 스크롤 밖에 두었다가 겪은 레이아웃 붕괴(`design-system.md` 14절)를 반복하지 않기 위해서도 필요하다.
- **텍스트 검색 추가** — 이름·장소·테이스팅 노트 대상. `DrinkRecordFilter`에 검색어 필드를 추가하고 DAO에 `LIKE` 절을 넣는다.
- **정렬 추가** — 최신순(현행)·별점순·가격순. DAO 쿼리에 정렬 파라미터가 필요하다.
- **필터 축 확장** — 태그(3.2에서 신설), 기간, 별점 범위. 가격 범위는 후순위.
- 하단 탭 왕복 시 필터가 유지되도록 내비게이션에 `launchSingleTop`/`popUpTo`를 적용한다.

### 3.4 주종 커스텀 설정

- `enabledDrinkTypes: Set<DrinkType>` 설정을 신설한다. 기본값은 3종 전체. **최소 1종은 남도록** 강제한다.
- 저장은 `ThemePreferenceRepository`와 동일한 SharedPreferences 패턴을 그대로 재사용한다(`drink_diary_preferences` 파일 공유).
- 영향 범위: 기록 화면의 주종 선택지, 컬렉션 필터의 주종 칩, 대시보드의 주종별 카드/비율 바에서 비활성 주종을 제외한다.
- **선행 리팩터링 필요**: `DashboardSummary`의 6개 하드코딩 필드를 `Map<DrinkType, TypeStat>` 형태로 바꾼다. 이 리팩터링 없이 주종 숨기기를 넣으면 1.4에 나열한 6곳을 매번 개별 수정해야 하고 누락이 발생한다.
- 이미 기록된 비활성 주종 데이터는 **삭제하지 않는다.** 집계에서 제외할지 여부는 설정 문구로 명확히 한다.

### 3.5 대시보드 인사이트 — 건강과 취향

**데이터 추가 (확정된 방식: 주종별 기본값 + 칩 보정)**

- `abv: Double?`, `volumeMl: Int?`를 `DrinkRecord`에 추가한다.
- 주종을 고르면 기본값이 자동 적용된다 — 맥주 5%/500ml, 와인 12%/150ml, 위스키 40%/30ml. **사용자가 아무 것도 하지 않아도 값이 채워진다.**
- 다르면 칩 한 번 탭으로 보정한다(용량: 330/500/1000ml, 도수: ±1% 단위 프리셋 + 직접 입력). 3.1의 "최소 4탭" 목표를 해치지 않는다.
- 기본값 사용 여부를 구분해 저장할지는 구현 시 결정한다(추정치임을 UI에 표시할 필요가 있는지의 문제).

**건강 축 지표**

- 순수 알코올(g) 환산: `volumeMl × (abv/100) × 0.789`.
- 주간 섭취량과 **일반적 권장 기준 대비 위치**. 경고가 아니라 사실 제시로 표현한다.
- 전주 대비 증감 — 현재 `periodRange`가 단일 기간만 계산하므로 **이전 기간 조회 로직 추가가 필요**하다.
- 연속 무음주일. 기존 `ObserveMonthRecordDatesUseCase`의 날짜 집합을 활용할 수 있다.
- **면책 문구 필수** — 의학적 조언이 아님을 명시한다.

**취향 축 지표**

- 3.2의 태그 빈도를 집계한 **선호 프로파일**(가장 자주 고른 향/맛 태그). 이것이 태그를 자유 서술 대신 선택형으로 만드는 핵심 이유다.
- 재구매 후보로 분류한 기록의 공통 태그 — "당신이 다시 사는 술의 공통점".
- 가격대별 만족도(별점 평균). `price`가 이미 있으므로 스키마 변경 없이 가능하다.

## 5. 구현 순서 제안과 리스크

### 권고 순서

1. **스키마 변경을 1회로 묶는다** — 3.2의 `tastingTags`와 3.5의 `abv`/`volumeMl` 추가, 그리고 `detailRating1..4` 정리를 **하나의 마이그레이션**으로 처리한다. DB 버전을 2 → 3으로 올리고 `DrinkDiaryDatabase.kt`에 `MIGRATION_2_3`을 추가하며, `app/schemas/`에 3.json이 생성되는지 확인한다(수동 편집 금지).
2. **`DashboardSummary` 리팩터링** — 3.4의 선행 조건. 스키마 변경과 독립적이므로 병행 가능하다.
3. **기록 UX (3.1)** — 별점 UI 교체는 스키마와 무관하므로 가장 먼저 체감 효과를 낼 수 있다.
4. **태그 UI (3.2)** — 1번 마이그레이션에 의존.
5. **필터 개편 (3.3)** — 태그 필터가 4번에 의존하므로 그 뒤. 검색·정렬만 먼저 떼어내는 것도 가능하다.
6. **주종 설정 (3.4)** — 2번에 의존.
7. **인사이트 (3.5)** — 1번과 4번에 의존하므로 마지막.

### 리스크

| 리스크 | 대응 |
| --- | --- |
| 기존 사용자의 `detailRating` 데이터 손실 | 마이그레이션에서 처리 방침을 **명시적으로 결정**한다. 디버그 시드 데이터가 있으므로 실기기/에뮬레이터에서 마이그레이션 전후를 실제로 검증한다 |
| 건강 지표가 의학적 조언으로 오인 | 면책 문구를 UI에 배치한다. Play Console 건강 관련 정책 저촉 여부를 출시 전 확인한다(`legal/` 참고) |
| 도수/용량 기본값의 부정확성 | 추정치임을 UI에서 구분한다. 주종별 기본값 자체를 사용자가 설정에서 바꿀 수 있게 하는 것도 후보 |
| 태그 어휘가 UI에 안 맞음 | 3.2에 적은 대로 8자 초과 칩을 반영 전 축약한다 |
| 대규모 UI 개편과 충돌 | 이 문서의 기능 방향이 먼저 확정되어야 개편 대상이 명확해진다. **기능 → UI 순서를 지킨다** |

## 6. 범위 밖 (변경 없음)

기존 `usecase.md` 2절의 제외 범위를 그대로 유지한다.

- 사용자 계정, 로그인, 서버 동기화
- 외부 주류 데이터베이스 연동
- 소셜 공유, 추천, 구매 링크, 재고 관리

추가로 이번 재정립에서도 다루지 않는 것:

- 세션(한 자리에서 여러 잔) 개념 — 현재 데이터 단위는 계속 "술 1종 = 기록 1건"이다
- 칼로리 추정 — 도수·용량으로 계산 가능하지만 이번 범위에 넣지 않는다
