## 1. 검증 결과

### 1-1. 날조 0건 [검증됨]

agy가 근거로 든 앱을 표본 검색했고 **전부 실재하며 설명도 정확했다.**

| 앱 | agy의 설명 | 확인 |
| --- | --- | --- |
| 북적북적 | "누적 높이를 시각화한 캐릭터 선반" | 책 탑을 쌓고 캐릭터 60종을 얻는 구조 — 일치 |
| 마이루틴 | "루틴 체크 + 주간 달성, 스트릭" | 루틴·습관·통계 올인원 플래너 — 일치 |
| Beli | "pairwise 비교로 개인 랭킹" | 과거 방문지와 비교해 순위를 매기는 방식 — 일치 |
| Vivino Taste Profile | "What you like vs what you dislike" | 아래 1-3 참고 — 일치 |

지난 두 번의 위임과 달리 **이번에는 출처 날조도, 조사와 결론의 불일치도 없었다.**

### 1-2. 누락 — 네 번째다. 그런데 성격이 달라졌다 [검증됨]

**프롬프트에 "국내(한국) 앱을 최소 5개 포함해라. 해외 앱만 나열하면 이 조사는 실패한 것이다"라고
명시했다.** agy는 국내 6종을 넣어 **개수는 지켰다** — 데일리샷, 와인그래프, 왓챠피디아,
하루콩, 북적북적, 마이루틴.

**그런데 우리와 같은 카테고리(국내 위스키/와인 기록 앱)는 하나도 없다.**
검색 한 번으로 아래가 전부 확인된다.

| 앱 | 성격 | 우리와의 관계 |
| --- | --- | --- |
| **글렌 — 위스키 테이스팅 노트** | 테이스팅 노트 기록·공유 | **가장 가까운 직접 경쟁** |
| **위스키키** | 테이스팅 노트. 병을 술장에 세우는 UI | 직접 경쟁. **구글 로그인 동기화 있음** |
| **위스키파크 = We!skey** | 31가지 맛·향 입력 + 쇼핑 | 직접 경쟁. `prd.md` 4절이 이미 지목한 앱 |

> **부수 확인**: `prd.md` 4절이 "위스키파크(31가지 맛·향)"라고 적은 것과 검색 결과의
> "We!skey — 31가지 맛과 향"이 **같은 앱**이다(Play 패키지 `com.weksey`). PRD 기술은 정확하다.

> **경쟁 정보 하나**: 위스키키는 **구글 로그인으로 리뷰를 저장·동기화**한다. 우리의 로컬 전용은
> 차별점인 동시에 **"폰 바꾸면 날아간다"는 약점**이기도 하다 — 백업이 왜 밀린 숙제인지의 근거가
> 하나 더 생겼다.

**교훈: 개수 제약은 카테고리 누락을 막지 못한다.**
1차(2026-08 시장 리서치)는 조건 없이 → 누락. 2차(4축 검증)도 누락. 3차(벤치마크)도 누락.
**4차는 "국내 5종 이상"을 걸었더니 국내 앱은 채우고 카테고리를 비웠다.**
→ 다음부터는 **조사 대상 앱 이름을 Claude가 지정해서 넘긴다.** 개수로 요구하지 않는다.

### 1-3. Vivino Taste Profile — agy의 P4를 뒷받침한다 [검증됨]

Vivino 공식 문서 확인 결과, 평가한 와인들로 **`What You've Tried` / `What You Like` /
`What You Dislike`**를 스타일·지역·품종별로 나눠 보여준다. 결정적으로 용례가 우리와 같다 —
**매장에서 꺼내 어떤 스타일을 좋아하는지 확인하는 용도**라고 공식 문서가 직접 적고 있다.

**이것이 우리 `라벨로 본 취향`이 가려는 방향과 정확히 같다.** 다만 Vivino는 이 화면을
프로필 안쪽에 두는데, 우리는 대시보드에 이미 노출하고 있다 — **위치는 우리가 낫다.**

## 2. agy의 진단 중 채택하는 것

agy가 지목한 세 약점은 **코드와 대조해 보면 사실이다.**

### ① 판정 전 구간이 결핍으로 말한다 — 사실이고, 이미 우리도 찾았다

화면 문구가 `"아직 취향을 판단하기엔 일러요"`다. 기록을 2~3잔 남긴 사용자에게 **첫 줄이
"당신의 데이터로는 아직 아무 말도 못 한다"**가 된다.

이건 `completeness-improvement-plan-2026-08.md` P1-5(판정관 톤)가 이미 지적한 것과 같은
지점이고, `branding.md` 4-5("중립을 결함처럼 말하지 않는다")와도 마찰한다.
**agy가 독립적으로 같은 결론에 도달했다는 것이 이 항목의 신뢰도를 올린다.**

`prd.md` F3은 이미 **"N개 미만에서도 화면이 비어 있지 않다"**를 요구한다. 지금 그 자리를
채우는 것은 진행 게이지 하나뿐이다 — **명세는 있고 구현이 얇다.**

### ② 판정 후 화면이 정체된다 — 사실이다. 다만 원인 진단은 반만 맞다

agy: "8번째, 12번째 잔을 마셔도 상단 50%가 고정된다."

**맞다.** 그런데 **유형이 잘 안 바뀌는 것은 결함이 아니라 설계다.** 취향이 매주 뒤집히면
그것이야말로 신뢰를 무너뜨린다(`software-architecture.md` 4-1이 "없는 취향을 지어내는" 문제를
풀면서 얻은 안정성이다).

**따라서 해법은 유형을 흔드는 것이 아니라, 정당하게 매번 달라지는 층을 하나 더 얹는 것이다.**
agy의 P2가 정확히 그 자리다.

### ③ 4글자 코드만으로는 자랑거리가 안 된다 — 사실이나 새 제안은 아니다

agy는 이것을 P3(공유 카드)으로 제안했는데, **우리 로드맵에 이미 F4로 있다**
(`mvp-scope.md` 3절, 9:16 카드, 유형이 주인공). agy는 그것을 몰랐을 뿐이다.
→ **새 기능이 아니라 착수 시점 문제로 분류한다.**

### P1의 문제 [충돌]

agy의 UI 개념도는 축값의 **산술 평균**("바디감 평균 1.5")을 보여준다.
**우리 판정은 평균이 아니라 축값과 만족도의 상관이다.** 평균을 취향처럼 배치하면
지난 벤치마크에서 이미 걸렀던 "달콤함 75%" 제안과 같은 오류가 된다 —
**화면이 근거라고 내놓는 숫자가 실제 판정 근거가 아니게 된다.**

**다만 판정 전 구간에 한해서는 쓸 수 있다.** 그 구간에서 보여줄 것은 취향이 아니라
**"내가 무엇을 어떻게 답했는가"의 되비침**이기 때문이다. 조건은 하나다 —
**그것을 취향이라고 부르지 않는 것.** "당신은 묵직한 걸 좋아해요"가 아니라
"지금까지 묵직한 쪽으로 답하셨어요"다.

### P4의 문구 문제 [충돌]

agy가 쓴 **"지뢰 키워드"**, "한 번 더 고민해보세요"는 `branding.md` 2-1의
"초보자 훈계 금지"와 마찰한다. **판정을 대신 내려주는 어조**다.
사실만 말하면 된다 — "버번 캐스크는 3잔에서 2.3점이었어요."

## 4. agy가 놓친 것 — Claude 추가

**대시보드에 "다음에 뭘 마셔볼까"가 없다.** agy의 네 제안은 전부 **과거를 더 잘 보여주는**
것이다. 그런데 이 제품의 존재 이유는 `problem-definition.md`가 적은 대로
**"그래서 다음 한 병을 무엇으로 고를까"**다.

우리 데이터로 할 수 있는 정직한 형태가 있다 — **아직 안 마셔본 조합을 말해주는 것.**
"셰리는 3잔 드셨는데 버번은 아직 없어요" 같은 문장은 남의 평점을 쓰지 않고, 지어내지도 않으며,
**다양성 부족이 판정을 막는다는 우리 자신의 문제**(`software-architecture.md` 4-2 IMPORTANT)를
사용자 언어로 옮긴 것이다.

**이것은 추천이 아니라 공백 안내다.** 추천은 남의 데이터가 필요하지만 공백은 내 기록만으로 안다.

## 5. Claude 종합 판단

**대시보드는 "이목을 끌 만한가"라는 질문에 지금은 아니다.** 다만 이유가 UI 장식의 부재가 아니다.

- **판정 전**: 명세(F3)가 요구하는 "비어 있지 않은 화면"을 진행 게이지 하나로 때우고 있다.
- **판정 후**: 매번 같은 결론이 최상단을 차지하고, **새 기록이 화면을 바꾸지 않는다.**
- **공통**: 화면 전체가 **과거형**이다. 다음 구매로 이어지는 문장이 하나도 없다.

**가장 값싼 순서는 P2 → 4절(공백 안내) → P4다.** 셋 다 입력 마찰 0이고 기존 데이터로 계산되며,
셋 다 **새 기록을 남길 때마다 화면이 실제로 달라진다.**

P1은 판정 전 구간 한정으로, 취향이라고 부르지 않는 조건에서만 쓴다.
P3(공유 카드)는 F4이므로 이 문서의 소관이 아니다.

> [!IMPORTANT]
> **어느 것도 PRD에 없다.** 다건 삭제 때와 같은 순서를 지킨다 — 착수 전에 F3-3을 신설하고
> 수용 기준을 먼저 쓴다. 코드가 PRD보다 앞서면 그 기능은 근거 없이 존재하게 된다.
