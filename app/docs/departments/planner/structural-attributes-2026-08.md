> [!NOTE]
> **상태: 초안 — 사용자 확정 전.** 조사: `agy`(`gemini-3.6-flash-high`, Product Planner 페르소나,
> conversation `4ff4f270-4a44-4047-9c1a-1eeff2d56860`), 검수: Claude.
> 함께 읽을 것: `axis-validation-2026-08.md`(감각 4축이 실패한 근거).

| 표기 | 뜻 |
| --- | --- |
| **[검증됨]** | Claude가 웹 검색으로 실재를 확인함 |
| **[미검증]** | agy가 출처를 댔으나 확인하지 않음. 사실로 취급하지 말 것 |
| **[출처 불명]** | 출처를 찾을 수 없음. 인용 금지 |

## 1. 검토 대상

기록할 때 **선택 입력**으로 아래를 채우고, 취향 판단에 함께 쓰는 안(사용자 제안, 2026-08-14).

- 위스키: 싱글몰트/블렌디드, 캐스크, 도수, 숙성 년수
- 와인: 레드/화이트/로제, 도수, 생산국, 품종

## 2. 결론 — 가장 값진 속성이 가장 못 넣는 속성이다

검토의 핵심은 이 교차다.

| 속성 | 취향 연결도 | 라벨에서 읽히는가 | 값 개수(실측) | 판정 |
| --- | --- | --- | --- | --- |
| 와인 품종 | **최상** | **구세계 불가** | 25 (최다 4종) | **사용자 입력 불가** |
| 위스키 캐스크 | **상** | **법적 표기 의무 아님** | 4(그룹핑 시) | **사용자 입력 불가** |
| 위스키 분류 | 중 | 가능 | 실질 3 | **쓸 수 있다** |
| 와인 색 | 중 | 가능 | 실질 2 | **쓸 수 있다** |
| 생산국 | 중 | 가능 | 10 → 2(구/신대륙) | **쓸 수 있다** |
| 도수 | 중 | 가능(법적 표기) | 8 → 3(구간화) | **쓸 수 있다** |
| 숙성 년수 | **하**(가격 지표에 가까움) | 34%가 표기 없음(NAS, 실측) | 11 → 4 | 약함 |

> **취향과 가장 강하게 연결된 두 속성(품종·캐스크)이, 사용자가 라벨에서 읽을 수 없는 바로 그 둘이다.**

따라서 사용자 태그만으로는 취향 판단의 핵심을 얻을 수 없다. 그 둘은 **앱이 미리 알고 있어야** 한다.

## 3. Claude가 놓쳤던 것 — agy의 기여

`axis-validation-2026-08.md`의 Claude 분석은 **카디널리티(값이 몇 개로 흩어지는가)**만 봤다.
agy는 그보다 앞서는 제약을 지적했다: **애초에 라벨에서 읽을 수 있는가.**

1. **구세계 vs 신세계 품종 표기 차이** — 신세계(미국·칠레·호주·뉴질랜드)는 라벨 전면에 품종을 크게
   적지만, 구세계(보르도·부르고뉴·키안티·리오하)는 원산지 명칭 제도상 **지역명만** 적는다.
   *"샤블리 = 샤르도네"*는 사전 지식이지 라벨 정보가 아니다.
   **우리 103종 데이터로 확인: 와인 39종 중 프랑스 15 + 이탈리아 9 = 24종(62%)이 구세계.**
   즉 품종 입력은 와인의 3분의 2에서 막힌다.

2. **캐스크는 법적 표기 의무가 아니다** — 국내 한글 백라벨에는 "원재료명: 위스키 원액"만 적힌다.
   일부 싱글몰트가 "Sherry Oak"를 마케팅으로 강조할 뿐이다.
   → Claude가 "캐스크는 4값으로 묶으면 쓸 수 있다"고 한 것은 **Claude가 배정한 값** 기준이었지,
   사용자가 읽을 수 있다는 뜻이 아니었다. **이 지적이 맞다.**

3. **경쟁 앱은 전부 DB 자동 바인딩** [검증됨 — 위스키키]
   국내 앱 위스키키는 *"위스키 이름을 검색하면 풀네임·종류·국가·이미지가 자동 입력되고,
   마신 방식(니트/스트레이트/온더락/하이볼)을 선택"*한다.
   사용자에게 메타데이터를 손으로 받는 앱은 확인되지 않았다.
   (참고: 그 앱의 '마신 방식' 항목은 우리 `ServingStyle`과 사실상 동일하다.)

## 4. agy 산출물의 문제 — 검증에서 걸러낸 것

### 4-1. 출처 날조 (이전 사고와 같은 양상)

| agy가 댄 출처 | 판정 |
| --- | --- |
| "위스키 라벨 표시 관행 실태 조사, 2024년" | **[출처 불명]** 기관명 없음. 인용 금지 |
| "국내 유통 위스키 라벨 실태 조사, 2024년" | **[출처 불명]** 동일 |
| "Vivino Merchant & User Guidelines 2024" 등 앱 3건 | **[출처 불명]** — 앱 자체는 [검증됨]이나 이런 문서명은 확인 불가 |
| "Whisky Advocate Tasting Guide, 2022년" | [미검증] 매체는 실재 |
| "WSET Level 2 Award in Wines Specification, 2023년" | [미검증] 자격·문서 형식은 실재 |
| "식품의약품안전처 주류 표시기준 고시, 2023년" | **[부분 검증됨]** — 주류 표시 관련 고시는 실재하고 도수 표시는 표준이나, 그 문서명·연도는 확인 못 함 |

**개선점**: 프롬프트에 "출처 없음 — 내 판단"을 허용했더니 agy가 실제로 여러 곳에서 그렇게 밝혔다
(숙성년수의 취향 연결, 카디널리티 추정치, 선택 입력 작성률 20% 추정). 이 문구는 계속 쓴다.

### 4-2. 국내 경쟁 앱 누락 (이전 사고와 같은 양상)

agy는 국내 앱 3개(와인그래프·데일리샷·한모금)만 보고했다. 검색 **한 번**에 아래가 추가로 나왔다.

- **글렌 — 위스키 테이스팅 노트** [검증됨]
- **위스키키 — 나만의 위스키 테이스팅 노트** [검증됨]
- **위스키파크** [검증됨]
- 와인일기, 토스트(오늘의 술 다이어리), 주룩 [검증됨]

**빠진 것 중 셋이 직접 경쟁하는 위스키 테이스팅 노트 앱이다.** 2026-08 시장 리서치 때와 동일한
실패(국내 경쟁사 1개 보고, 실제 5개 이상). → **agy 리서치는 국내 서비스를 체계적으로 누락한다.
이 항목은 앞으로 항상 Claude가 직접 교차 검색한다.**

또한 agy는 앱 이름을 "와인그라프"로 적었으나 실제는 **와인그래프**다.

### 4-3. 자기 조사와 결론의 불일치

1. **캐스크에만 구간화를 적용하지 않았다.** agy는 도수·품종에는 구간화를 제안하면서, 캐스크는
   "20개 이상 파편화 → 부적합"으로 잘랐다. 우리 실측으로는 **버번/셰리/새오크/혼합 4값**이면
   64종이 덮인다. 파편화는 원본 라벨 표기의 문제지 속성 자체의 문제가 아니다.
   (다만 4-1의 "라벨에서 못 읽는다"는 지적은 별개로 유효하다.)

2. **카디널리티와 채움률을 결합하지 않았다.** agy는 §2에서 값 개수를, §5-1에서 채움률 20%를
   각각 분석했지만 둘을 곱하지 않았다. 실행 가능성은 그 곱이 정한다.
   **Claude 실측**: 20잔 기준 값 2개 속성은 채움률 30%에도 각 3건이 모이고, 값 6개 이상은
   채움률 100%여도 각 3.3건에 못 미친다. 즉 "취향 엔진 마비"는 **저카디널리티 속성에는 해당하지 않는다.**

3. **"전면 철회" 표현이 자기 제안과 어긋난다.** 종합 판단은 "전면 철회되거나 전면 수정"이라 했지만,
   agy 자신의 제안 ②는 선택 입력을 **2개로 줄여 유지**한다. 실제 결론은 "축소 유지"다.

## 5. Claude의 반론과 종합

**agy에 동의하는 부분**

- 품종·캐스크는 사용자 입력 대상이 아니다. 라벨에서 읽히지 않는다.
- 숙성 년수는 취향 지표가 아니라 가격 지표에 가깝다. 판단 축에서 뺀다.
- 경량 큐레이션 DB를 내장하자는 제안(③)은 타당하다. 오프라인 제약과 충돌하지 않는다.
  **우리는 이미 103종 데이터셋을 갖고 있다** — 감각 축 검증용으로 만든 것이 그대로 씨앗이 된다.

**agy와 다른 부분**

- "선택 입력 전면 철회"는 과하다. **라벨에서 읽히고 값이 적은 속성**(위스키 분류, 와인 색,
  도수 구간, 구/신대륙)은 채움률이 낮아도 판단에 쓸 수 있다. 실측 근거는 §4-3-2.
- 피트 유무는 agy도 제안했고 Claude 실측(L47/M10/H7)과도 맞는다. **지각 가능하면서 동시에
  범주형인 유일한 속성**이라 태그로 받기에 가장 적합하다.

**정리**

| 경로 | 속성 |
| --- | --- |
| **사용자 태그로 받는다** | 위스키 분류, 피트 유무, 와인 색, 도수 구간, 구/신대륙 |
| **앱이 미리 안다(내장 DB)** | 품종, 캐스크 |
| **취향 판단에서 뺀다** | 숙성 년수(가격 지표), 생산국 원본 10값·품종 원본 25값(표본 부족) |
| **입력은 받되 판단에 안 쓴다** | 생산국 상세, 품종 상세 — 기록·조회의 가치는 있다 |

## 6. 열린 문제

1. **내장 DB의 범위와 갱신** — 100종으로 시작할지, 그 이상인지. 신제품은 어떻게 할지.
   앱 업데이트로만 갱신되는 것을 수용할지.
2. **DB에 없는 술** — 사용자가 직접 등록할 때 태그 경로로 떨어진다. 이때 5탭 예산을 어떻게 지킬지.
3. **PRD F3 "자신의 기록에서만 도출" 원칙** — 내장 DB의 속성을 판단에 쓰면 이 원칙과 충돌한다.
   *속성은 술의 사실이고 만족도는 여전히 사용자 것*이라는 해석으로 지킬 수 있는지 판단 필요.
