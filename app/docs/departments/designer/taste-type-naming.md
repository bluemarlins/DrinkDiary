> [!NOTE]

## 1. 제약 조건

작명은 취향이 아니라 **규칙**의 문제로 다룬다. 아래 넷을 모두 만족해야 한다.

| # | 제약 | 출처 |
| --- | --- | --- |
| 1 | **4축에서 체계적으로 파생**될 것. 손으로 빚은 16개 페르소나 금지 | 축이 바뀌어도 무너지지 않아야 한다 |
| 2 | **역추적 가능**할 것. 코드를 보고 "왜 이 유형인지" 알 수 있어야 한다 | 쟁점 6 — 신뢰 |
| 3 | **우열이 없을** 것. 어떤 유형도 더 좋거나 고급이지 않다 | 쟁점 6 — 게임화 금지 |
| 4 | **짧고 말해질 수 있을** 것 | F4 공유 카드의 동력 |

제약 1과 4는 서로 당긴다. 체계적일수록 기계적이고, 매력적일수록 자의적이다. 아래 안은 그 사이를
**코드는 체계적으로, 설명은 파생적으로** 나눠서 푼다.

## 2. 제안 — 4글자 코드

각 축이 한 글자씩 낸다. 8개 글자가 서로 충돌하지 않도록 골랐다.

| 축 | 한쪽 | 반대쪽 |
| --- | --- | --- |
| Sweetness | **S** — 달콤 (Sweet) | **D** — 드라이 (Dry) |
| Body | **F** — 묵직 (Full) | **L** — 가벼움 (Light) |
| Intensity | **R** — 진함 (Rich) | **M** — 은은함 (Mild) |
| Aftertaste | **E** — 긴 여운 (Enduring) | **Q** — 산뜻 (Quick) |

**축 순서는 고정한다: Sweetness → Body → Intensity → Aftertaste.**
예: `DFRE` = 드라이 · 묵직 · 진함 · 긴 여운

16개 전체: SFRE SFRQ SFME SFMQ SLRE SLRQ SLME SLMQ DFRE DFRQ DFME DFMQ DLRE DLRQ DLME DLMQ

### 왜 4글자 코드인가

- **제약 1·2를 동시에 만족하는 유일한 형태다.** 코드 자체가 파생물이라 축이 바뀌면 코드도 자동으로
  바뀐다. 사용자는 글자 하나하나를 축으로 되짚을 수 있다.
- **제약 3을 구조적으로 만족한다.** `SFRE`가 `DLMQ`보다 낫다고 말할 근거가 코드 어디에도 없다.
  반면 별칭("깊이의 탐험가" 같은)을 붙이는 순간 우열의 뉘앙스가 새어든다.
- 한국 사용자에게 4글자 코드는 이미 익숙한 형식이다(제약 4).

## 3. 이름과 설명 — 파생 생성

별칭을 손으로 짓지 않는다. **축 값에서 문구를 조립**한다.

```text
짧은 이름 = {Body}{Intensity} 취향        (2축만 — 가장 지각하기 쉬운 축)
한 줄 설명 = {Sweetness}하고 {Body}하며, {Intensity} 향에 {Aftertaste}
```

| 축 | 값 | 이름 조각 | 설명 조각 |
| --- | --- | --- | --- |
| Sweetness | S / D | — | 달콤 / 드라이 |
| Body | F / L | 묵직한 / 가벼운 | 묵직 / 가벼움 |
| Intensity | R / M | 진한 / 은은한 | 진한 / 은은한 |
| Aftertaste | E / Q | — | 여운이 길다 / 산뜻하게 끝난다 |

**예시**

| 코드 | 짧은 이름 | 한 줄 설명 |
| --- | --- | --- |
| `DFRE` | 묵직한 진한 취향 | 드라이하고 묵직하며, 진한 향에 여운이 깁니다 |
| `SLMQ` | 가벼운 은은한 취향 | 달콤하고 가벼우며, 은은한 향에 산뜻하게 끝납니다 |
| `DLRQ` | 가벼운 진한 취향 | 드라이하고 가벼우며, 진한 향에 산뜻하게 끝납니다 |

짧은 이름이 2축만 쓰는 이유: 4축을 모두 넣으면 길어져 말해지지 않는다(제약 4). Body와 Intensity를
고른 것은 **입문자가 가장 뚜렷하게 지각하는 축**이기 때문이다 — 다만 이는 **가설이며 F2
프로토타입에서 확인해야 한다.**

## 4. 표시 규칙

- **코드와 이름은 항상 함께 보여준다.** 코드만 있으면 무슨 뜻인지 모르고, 이름만 있으면 역추적이
  안 된다.
- 유형 화면에서는 **글자별로 어느 축인지 펼쳐 보여준다.** 사용자가 자기 유형을 납득해야 공유한다.
- **다른 유형과 비교하거나 분포·희귀도를 표시하지 않는다.** "당신은 상위 3% 유형" 같은 표현은
  쟁점 6 위배다.
- 유형이 아직 없을 때는 빈 코드 자리를 보여주고 남은 거리를 함께 표시한다.

## 5. 열어둔 문제

1. **영문 코드가 맞는가** — 한글 코드(예: `드묵진길`)도 가능하다. 영문이 짧고 익숙하지만 국내
   서비스에 영문 코드가 이질적일 수 있다. **A/B로 볼 가치가 있다.**
2. **짧은 이름의 2축 선택** — Body×Intensity가 가장 지각하기 쉽다는 것은 가설이다.
   F2 프로토타입에서 실제로 어느 축을 사용자가 확신 있게 답하는지 보고 정한다.
3. **통합 유형의 표기** — 와인 유형과 위스키 유형이 다를 때 통합 유형을 어떻게 낼지.
   단순 합산인지, 두 유형을 나란히 보여주는지. **Pro의 핵심 상품이므로 별도 설계가 필요하다.**
4. **별칭 도입 여부** — 지금은 도입하지 않는다. 데이터가 쌓여 유형 분포를 본 뒤,
   제약 3(우열 없음)을 지킬 수 있다는 확신이 설 때 재검토한다.
