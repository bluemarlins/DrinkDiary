# agy 위임 리서치 + 검증

`agy` 산출물은 신뢰하지 않은 것으로 취급한다(`app/docs/orchestration/harness.md` §5).
이 스킬은 위임부터 검증·기록까지의 절차를 고정한다.

## 이 절차가 존재하는 이유 (실제 사고)

2026-08 시장 리서치에서 `agy`가 *"Atomin User Engagement Analysis, 2024"*라는 출처를 대며
"공유 카드가 앱 삭제율을 낮추는 효과가 증명되어 있다"고 보고했다. **그 출처는 존재하지 않았다.**
하필 그 주장이 제품 방향의 핵심 근거였다. 검증 없이 넘어갔다면 허위 근거 위에 PRD가 세워졌다.

같은 조사에서 국내 경쟁 앱을 1개만 보고했으나 실제로는 최소 5개가 있었고, 스스로 보고한 시장 하락
지표를 결론에서 누락했다.

→ **`agy` 리서치의 실패 양상은 세 가지다: 출처 날조, 누락, 자기 조사와 결론의 불일치.**
   아래 절차는 이 세 가지를 각각 잡는다.

## 1단계 — 위임 전 확인

`AGENTS.md`의 위임 4조건을 모두 만족하는지 본다. 하나라도 아니면 Claude가 직접 한다.

1. 조사 범위가 이미 정해졌는가 (agy가 무엇을 조사할지 스스로 정하게 두지 않는다)
2. 결과를 검증할 수 있는가
3. 파일 수정이 필요 없거나 `--add-dir`로 범위를 좁힐 수 있는가
4. 결과가 나빠도 버리고 다시 하면 되는가

모델은 로스터 4개 중에서만 고른다(`harness.md` §6-2). 리서치는 보통 `gemini-3.7-flash-high`,
정형 요약만 필요하면 `gemini-3.7-flash-medium`.

**모델이 새것이라고 검증을 줄이지 않는다.** 위 세 실패 양상은 모델의 성능 문제가 아니라 위임
구조의 문제라 세대가 올라가도 그대로 남는다. 실제로 2026-08-15 병 사전 구축에서 agy가 처음으로
깨끗한 결과를 낸 것은 모델을 바꿔서가 아니라 **채울 필드를 둘로 좁혀서 검증이 가능해졌기
때문이다** — 100줄짜리 사실 데이터를 통째로 받으면 어느 세대의 모델이든 검증할 수 없다.

## 2단계 — 프롬프트에 반드시 넣을 것

```text
[Persona] 너는 '테이스트 아카이브' 프로젝트의 <부서명>다.
          persona-registry.artifact.md의 정의를 따른다.

[정직성 규칙] 추측을 사실처럼 쓰지 마라. 근거를 찾지 못한 항목은 "확인 불가"라고 명시해라.
             모든 수치에는 출처(기관명, 조사연도)를 붙여라.

[중요] 파일을 수정하지 마라. markdown 보고서를 표준 출력으로만 내라.

[제품 맥락] <타깃, 해결하려는 문제, 범위를 3~5줄로>

[조사 항목] <번호를 매긴 구체적 항목. 각각 별도 섹션으로 요구>
```

"확인 불가"를 허용하는 문구가 **핵심이다.** 이 문구가 없으면 모델은 빈칸을 지어내서 채운다.
실제로 이 문구를 넣었을 때 "연간 구매 병 수: 확인 불가"라는 정직한 회신이 돌아왔다.

호출 예:

```bash
agy -p "$(cat <<'PROMPT'
<위 템플릿>
PROMPT
)" --model gemini-3.7-flash-high --output-format json
```

**한 번에 하나만 실행한다.** 동시 호출 금지(`harness.md` §5 사고 이력).

## 3단계 — 검증 (생략 금지)

산출물을 읽고 아래를 순서대로 한다.

### (1) 출처 검증 — 날조 탐지

**모든 고유명사 출처를 WebSearch로 확인한다.** 특히:

- 처음 보는 기관·리포트명 → **반드시 검색.** 없으면 `[출처 불명]`으로 표시하고 **인용 금지**
- 우리 결론을 가장 강하게 뒷받침하는 주장 → **가장 먼저 검증.** 듣고 싶은 말일수록 의심한다
- 구체적 수치(백분율, 금액, 사용자 수) → 최소한 출처 실재 여부는 확인

### (2) 누락 탐지 — 직접 교차 검색

agy가 제시한 목록(경쟁사, 사례 등)을 그대로 믿지 않는다. **같은 주제로 직접 1~2회 검색**해
빠진 항목이 있는지 본다. 국내 서비스는 특히 잘 누락된다.

### (3) 일관성 검사 — 조사와 결론의 불일치

본문에 있는 불리한 지표가 결론에 반영됐는지 확인한다. agy는 결론을 낙관적으로 쓰는 경향이 있다.
본문이 시장 축소를 말하는데 결론이 "기회 있음"이면 그 결론은 신뢰할 수 없다.

## 4단계 — 기록

`app/docs/departments/<부서>/`에 저장한다(`specs/`가 아니다 — 초안이다).
문서 서두에 **상태 배지와 등급 표기 규칙**을 넣는다.

```markdown
> [!NOTE]
> **상태: 초안 — 사용자 확정 전.** 조사: `agy`(<모델>, <부서> 페르소나), 검수: Claude.

| 표기 | 뜻 |
| --- | --- |
| **[검증됨]** | Claude가 웹 검색으로 실재를 확인함 |
| **[미검증]** | agy가 출처를 댔으나 확인하지 않음. 사실로 취급하지 말 것 |
| **[출처 불명]** | 출처를 찾을 수 없음. 인용 금지 |
```

그리고 **Claude의 반론 절을 반드시 둔다.** agy 결론을 그대로 옮기지 않고, 동의/부분 동의/반대를
근거와 함께 적는다. 검증에서 무너진 주장이 다른 문서의 근거로 쓰이고 있다면 그 문서에도
교차 참조를 남긴다.

마지막으로 `app/docs/orchestration/task-log.md`에 사용 모델과 conversation id를 남겨 재현 가능하게
한다.

## 하지 말 것

- 검증 없이 산출물을 `specs/`에 올리기
- agy의 종합 의견을 그대로 결론으로 채택하기
- "확인 불가" 회신을 실패로 보고 추정치로 메우기 — 그 회신이 정답인 경우가 많다
- 여러 `agy` 호출을 동시에 띄우기
